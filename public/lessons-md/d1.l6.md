# D1.L6 — Pipelines

_Track D1: DataEngine Foundations · ~18 min · functionspace_

> A pipeline manifest is three lists — what to deploy, what triggers exist, and which events go where — plus the knobs that decide how many copies of your function run and how long each may take.
D1.L2 said a pipeline is the only object that makes code run. Here is what it contains. A pipeline targets one Kubernetes compute cluster and namespace, and its **manifest** has three lists:

- **function_deployments** — which function, which revision, what resources, how many concurrent copies, what timeout.
- **triggers** — which trigger objects this pipeline uses, each given a local name.
- **links** — which triggers' events flow to which deployments, over which topic, with what delivery settings.

---

```yaml
name: alice-tick-pipeline                 # required here — see the callout
kubernetes_cluster_vrn: vast:dataengine:kubernetes-clusters:<K8S_CLUSTER>
namespace: <NAMESPACE>
manifest:
  function_deployments:
    - function_vrn: vast:dataengine:functions:alice-echo
      name: alice-echo-1                    # local name, used by links
      revision: 1
      config:
        log_level: INFO
      resources:
        min_cpu: 100m
        max_cpu: 500m
        min_memory: 256Mi
        max_memory: 512Mi
        min_concurrency: 1
        max_concurrency: 2
        timeout: 60
  triggers:
    - name: alice-tick-1                    # local name
      vrn: vast:dataengine:triggers:alice-tick
  links:
    - source: [alice-tick-1]
      destination: [alice-echo-1]
      topic: vast:dataengine:topics:<BROKER>/<TOPIC>
      config:
        events_order: unordered
        retries: 3
```

---

## function_deployments: the scaler, declared

This block is where F0.L1's third mechanism lives for DataEngine:

| field | meaning | Knative cousin |
|---|---|---|
| `revision` | which published function revision to run | the Revision a Route points at |
| `min_cpu` / `max_cpu`, `min_memory` / `max_memory` | resource request and limit per copy | `resources.requests` / `limits` (K1.L6) |
| `min_concurrency` / `max_concurrency` | how many copies may run | `min-scale` / `max-scale` (K1.L4) |
| `timeout` | seconds one invocation may take | `timeoutSeconds` (K1.L6) |
| `config.log_level` | the runtime's log level | — |

Note what a deployment names: a function **and a revision number**. Publishing revision 2 of a function changes nothing running until a pipeline deployment is moved to `revision: 2` (lab 10, D2.L3). That is the same separation as Knative's Configuration and Route (K1.L1).

---

## links: the event path, declared

A link says: *events from these triggers, arriving on this topic, go to these deployments*. Its `config` carries the delivery policy — `events_order` (`unordered` or ordered delivery; compare K2.L5) and `retries`. `source` and `destination` are lists, so one trigger can fan out to several deployments and several triggers can feed one.

## Creating and deploying

```bash
vastde pipelines create --config pipeline.yaml --deploy     # create + deploy in one step
vastde pipelines get alice-tick-pipeline                     # status
vastde pipelines get alice-tick-pipeline --manifest          # the manifest as stored
vastde pipelines update alice-tick-pipeline --config @pipeline.yaml   # change it
```

`--dry-run` on `create` prints the request without contacting VMS — use it to catch YAML mistakes before they reach the server.

---

> **[warning]** Observed with v5.5.0-sp2: a manifest without a top-level `name` is refused even when `--name` is given on the command line — `failed to parse config as JSON or YAML: no value given for required property name` — and without either the client reports `validation failed: [name is required]`. Keep the name in the manifest, which is where it belongs anyway if the file is in git.

_fig 1 — the manifest, drawn_

Components: trigger (alice-tick-1) · trigger ((more, optional)) · link (topic · order · retries) · deployment (alice-echo rev 1) · deployment ((more, optional)) · pods (1–2 copies)

Steps:
1. The triggers list gives each trigger object a local name inside this pipeline. The trigger itself is still a separate object (D1.L5).
2. A link connects trigger names to deployment names through one topic, with its own delivery config: ordering and retries.
3. Each function deployment names a function and a revision, and gives it resources, a concurrency range and a timeout.
4. Deploying the pipeline turns each deployment into running copies on the compute cluster, between min and max concurrency. Nothing ran before this step.

**Q1. You publish revision 2 of a function. Its pipeline keeps running revision 1. Why, and is that a problem?**
   A. A bug — publishing should update every pipeline
   B. By design: a function deployment names a revision; moving it to revision 2 is a separate, deliberate pipeline update — the same separation as Knative Configuration vs Route
   C. Revision 2 failed to build
   D. Pipelines only run revision 1
   Answer: B — Separating "what exists" from "what runs" is what makes rollouts and rollbacks controlled. D2.L3 and lab 10 do the move deliberately.

**Q2. A handler takes up to 90 s on large objects; the pipeline has timeout: 60. What should you expect, and what do you change?**
   A. Nothing — timeout is advisory
   B. Invocations over 60 s are cut off and treated as failures (and retried per the link's retries); raise timeout above the real worst case, or split the work
   C. The pipeline will auto-extend the timeout
   D. Increase max_concurrency
   Answer: B — Timeouts bound one invocation. A timeout below the real worst case turns slow-but-correct work into failures and retries — the K1.L6 lesson, on a different platform.

**Q3. A team sets max_concurrency: 1 on a pipeline processing uploads and sees a growing backlog during business hours. What is the first number to check before raising it?**
   A. The trigger's cron schedule
   B. Arrival rate × handler duration (Little's law): if that exceeds 1, one copy cannot keep up by definition
   C. The registry size
   D. The log level
   Answer: B — Concurrency needed ≈ events per second × seconds per event. X1.L2 turns this into a sizing method; here it tells you whether max_concurrency is the bottleneck.
