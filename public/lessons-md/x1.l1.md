# X1.L1 — The Mapping

_Track X1: Two Platforms, One Model · ~18 min · functionspace_

> The DataEngine runtime reads K_SINK, answers Knative queue-proxy's HTTP/2 probe, and the installer embedded in the public CLI ships the Knative Operator and grants DataEngine's controller the right to create Knative Services, Brokers, Triggers and SinkBindings. Nobody has to tell you what is underneath — the artefacts do.
You now know two platforms. This lesson lays one over the other, object by object, and is strict about how each claim is known — because "DataEngine is just Knative" and "DataEngine is nothing like Knative" are both things people will say to you with confidence, and neither is a statement you can defend without evidence.

Four grades here — the course's usual three, plus one this lesson adds:

- **Documented** — VAST says so publicly.
- **Observed** — seen through the public `vastde` CLI and builder, on a real tenant or in the locally built function image.
- **Installer** — read from the manifests `vastde install --dry-run` renders from the chart embedded in the public CLI.
- **Inferred** — a reasonable conclusion from the evidence, with the command that would confirm it on your cluster.

---

## The object map

| DataEngine | Knative cousin | how the two differ | grade |
|---|---|---|---|
| **function** (image + numbered revisions, published) | container image + **Revision** | a DataEngine revision is published explicitly; a Knative revision is stamped from every template change | observed |
| **pipeline function_deployment** (revision, resources, min/max concurrency, timeout) | **Service** template + scale bounds + `timeoutSeconds` | a deployment names a revision number; Knative routes by Route traffic table | installer RBAC + observed |
| **trigger** (schedule, element) | **source** (PingSource; an S3 adapter) | element triggers are built into the storage; Knative needs an adapter | documented |
| **topic** on the event broker | **Broker** / **Channel** (Kafka-backed) | VAST documents the broker as Kafka-compatible; the installer reads Knative Kafka consumer groups | documented + installer |
| **link** (trigger → deployment, ordering, retries) | **Trigger** / **Subscription** + delivery spec | links route by trigger identity; Knative triggers filter by attributes | installer RBAC + observed |
| **dead-letter topic** (`setup-dataengine`) | **deadLetterSink** | configured per DataEngine installation vs per trigger | documented |
| **handler return value → K_SINK** | a subscriber **reply** / SinkBinding sink | DataEngine answers 204 and POSTs the value to the sink; Knative puts the reply in the HTTP response | runtime source + installer RBAC (SinkBindings) |

## The runtime is written for Knative

Lab 07 built the DataEngine Python runtime into an image. Its source, under `site-packages/vast/dataengine/runtime/`, contains:

- `return ENV_VARS.get("K_SINK")` — the sink URL comes from **`K_SINK`**, the variable Knative's SinkBinding and ContainerSource inject (K2.L1).
- `K_CE_OVERRIDES` parsed as JSON into outgoing event attributes, with the warning text *"failed parsing knative CE overrides"* — Knative's ContainerSource convention.
- A readiness endpoint that also answers `OPTIONS`, documented in the code as *"used by Knative queue-proxy to detect if the container supports HTTP/2"*.
- Port **8080**, `/readiness` and `/liveness` — the shape Knative Serving expects of a user container.

And lab 07's build log showed the image is built by **Paketo buildpacks** on the same run-image family as `func`'s default builder (K3.L2).

## The installer says the rest

`vastde install` installs DataEngine onto a Kubernetes cluster from a Helm chart **embedded in the public binary**. `vastde install --dry-run` renders it without applying anything — no VAST cluster or tenant needed. On v5.5.0-sp2 the rendered manifests contain:

- a `knative` subchart that deploys the **Knative Operator v1.20.0** (`gcr.io/knative-releases/knative.dev/operator/cmd/operator:v1.20.0`), creates the `knative-serving` namespace and runs Serving's default-domain job;
- VAST's own `vast-dataengine-controller-manager` and `vast-dataengine-collector`, and custom resources in `vast.vastdata.com`: **VastPipeline**, **VastKafkaBroker**, **VastTenant**;
- a ClusterRole for the controller manager whose rules are annotated in the chart itself:

---

```yaml
# VAST namespaced CRs (VastPipeline, VastKafkaBroker)
- apiGroups: [vast.vastdata.com]
  resources: [vastpipelines, vastkafkabrokers]
# Knative Eventing (Brokers, Triggers)
- apiGroups: [eventing.knative.dev]
  resources: [brokers, triggers]          # create, delete, get, list, patch, update, watch
# Knative Serving (Services)
- apiGroups: [serving.knative.dev]
  resources: [services]                   # create, delete, …
# Knative Sources (SinkBindings)
- apiGroups: [sources.knative.dev]
  resources: [sinkbindings]               # create, delete, …
# Knative Kafka ConsumerGroups (required by knativeconsumergroup reconciler)
- apiGroups: [internal.kafka.eventing.knative.dev]
  resources: [consumergroups]
```

---

Put that next to the runtime and the picture closes: a **VastPipeline** is reconciled by DataEngine's controller into Knative **Services** (function deployments), Kafka-backed **Brokers** and **Triggers** (topics and links), and **SinkBindings** — which is exactly why the runtime finds its return-value destination in `K_SINK`.

_fig 1 — the same event path, two vocabularies_

Components: source (PingSource / adapter) · Broker (channel / Kafka) · Trigger (filter + delivery) · Service → Revision (queue-proxy + container) · trigger (schedule / element) · topic (event broker) · link (order + retries) · deployment (rev N) (runtime on :8080)

Steps:
1. Knative: a source emits CloudEvents into a broker; a trigger filters and delivers them to a Service, whose current revision runs your container behind queue-proxy.
2. DataEngine: a trigger emits CloudEvents onto a topic; a pipeline link delivers them to a function deployment pinned to revision N, whose runtime listens on 8080.
3. The sources line up: a PingSource is a schedule trigger; an S3 adapter is an element trigger that needs no adapter because the storage emits it.
4. The transport lines up: a Kafka-backed broker and a Kafka-compatible topic share the partition and ordering model of K2.L5.
5. The last hop lines up most closely of all: the DataEngine runtime reads Knative's K_SINK and answers queue-proxy's probes — the contract is Knative-shaped.

## Where the analogy breaks

- **Routing.** Knative triggers filter on event attributes, so any consumer can subscribe to anything on a broker. DataEngine links connect named triggers to named deployments inside one pipeline — more explicit, less ad hoc.
- **Rollout.** Knative splits traffic by percentage across revisions (K1.L5). A DataEngine deployment names one revision; you move it (D2.L3).
- **Replies.** A Knative subscriber's reply goes back in the HTTP response and into the broker. A DataEngine handler's return value goes to `K_SINK`; the caller gets 204.
- **Scaling signal.** Knative's KPA scales on requests in flight with documented windows (K1.L3). DataEngine exposes `min_concurrency`/`max_concurrency`; how it decides between them is not documented — measure it (D2.L4, capstone).

---

_Python lifecycle, both platforms_

- **Knative Functions: start(cfg)** (Once per instance, before traffic; readiness waits for it.) ≡ **DataEngine: init(ctx)** (Once per container, before "ready to accept requests".)
- **Knative Functions: handle(scope, receive, send)** (Per event; reply by send(event); exceptions → 500.) ≡ **DataEngine: handler(ctx, event)** (Per event; return value → K_SINK; exceptions → 500; success → 204.)

**Q1. A colleague says "DataEngine runs on Knative, so the KPA's 60-second stable window applies to our pipelines." How do you respond?**
   A. Agree — the installer proves it, so the defaults must be the Knative defaults
   B. The installer and runtime show Knative underneath, but the operator-managed configuration (and how DataEngine maps min/max concurrency onto it) may differ from upstream defaults; read config-autoscaler on the compute cluster or measure before relying on 60 s
   C. Disagree — DataEngine has nothing in common with Knative
   D. The stable window is 30 seconds on DataEngine
   Answer: B — Knowing the component is not knowing its configuration. The Knative Operator lets DataEngine set its own values. Quoting upstream defaults as yours is how capacity plans go wrong — say what you know, how you know it, and what you would check.

**Q2. Which DataEngine concept corresponds to a Knative trigger's deliver-with-retries behaviour?**
   A. The function
   B. A pipeline link and its config (retries, events_order)
   C. The compute cluster
   D. The bucket
   Answer: B — Links carry events from triggers to deployments with a delivery policy — the role a Knative Trigger (subscription + delivery spec) plays.

**Q3. You want to confirm whether your DataEngine installation runs pipelines on Knative. What is the most direct check?**
   A. Read VAST marketing pages
   B. Render the installer with vastde install --dry-run to see what it deploys, then, with kubectl access to the compute cluster, deploy a pipeline and look for the Knative objects in the pipeline namespace
   C. Run vastde status
   D. Check the function's requirements.txt
   Answer: B — The installer tells you what could exist; the live objects tell you what does. vastde status reports Helm release state, which hints but does not show your pipeline's objects.
